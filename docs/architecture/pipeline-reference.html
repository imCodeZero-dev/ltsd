01 The full pipeline

Every one of the 8 schedules funnels through one shared Lambda, into 4 route targets, sharing one Keepa token budget and one Postgres connection pool. That sharing is exactly what has caused the last three production bugs — read the diagram as "what do these jobs actually compete for," not just "what calls what."

03 Token budget

Every route checks getLastKnownTokens() before running and skips (logs a WARNING, not a failure) if the pool can't cover it. That's expected, routine behavior — total daily demand across all jobs is higher than the pool, by design, so some skipping is normal.

05 Cleanup & expiry — the four functions that decide what "active" means

All four live in src/lib/deal-api/sync.ts and only markMissedDeals predates this build cycle.

  • markMissedDeals(seenAsins) — increments a miss counter on active, non-lightning deals not seen in the latest sync; deactivates at 3 consecutive misses. Lightning deals are explicitly excluded — they're handled directly by their own expiry check inside syncLightningDeals().
  • cleanupInvalidDeals() — deactivates anything with currentPrice ≤ 0. Added Aug 4 after a Keepa test/sample ASIN ($TEST$VineProdBrand-3) reached production and got featured as a real Deal of the Week.
  • cleanupExpiredDeals() — deactivates anything with expiresAt in the past, regardless of type. Added Aug 9 after 36,042 deals were found sitting active well past expiry. Runs once daily inside daily-sync — the frontend's own query-time filter (isActive:true AND not-expired) is the real safety net in the ~24h between runs.
  • cleanupStaleDealData() — hard-deletes anything inactive for 7+ days and not on anyone's watchlist. Pre-existing; not new this cycle.

06 Rainforest migration — live since 2026-08-19 ~00:36 PKT

Client asked to move off Keepa (too few deals, not real-time) onto Rainforest API. Built on feature/rainforest-migration as a second, fully parallel DealApiProvider implementation. Not a full replacement — split by job, based on real measured evidence of where each provider is actually better: category deals and lightning deals run through Rainforest (DEAL_API_PROVIDER=rainforest), while bestsellers, brand/pref sync, and daily price maintenance stay hard-pinned to Keepa in code regardless of that switch. Everything below was verified against real API responses, not docs alone, per the migration's own safety rule.

ⓘ Live config, EventBridge (Asia/Karachi execution tz): ltsd-category-feed → cron(0 3,15 * * ? *), 2x/day, 4 pages/category (120 items, 4 credits/category, confirmed via real test). ltsd-lightning-pm → cron(0 0,6,12,18 * * ? *), every 6h. Deliberately offset from category-feed's times so the two never fire simultaneously — running heavy syncs concurrently caused a real 504 timeout earlier in this project (see 2026-08-11 entries below). ltsd-bestsellers, ltsd-pref-brands, ltsd-maintenance unchanged, still Keepa. Plan: Rainforest Starter, $83/mo, 10,000 credits — Hobbyist (500/mo) was tested against the real numbers and ruled out as too small even for a narrow slice of this.
⚠ Real lightning-deal duration, not assumed: checked all 30 live lightning deals on 2026-08-18 — every one ran 11.5–12.0 hours, not the commonly-assumed "4–12 hour" range (that range was repeated once in this project without being checked against this app's actual data, then corrected). The consistent ~12h cycle is why every-6-hours was chosen for ltsd-lightning-pm — it catches each deal roughly twice in its lifetime. Cold-start categorization cost is confirmed at up to 31 credits/run (1 list + up to 30 per-ASIN lookups, no batching); steady-state cost is estimated at ~16/run from the 12h/6h math but has not yet been confirmed by real multi-day observation — this is the single biggest open number in the whole budget and the first thing to check once real usage data exists.
⚠ The discount parameter is a MAXIMUM, not a minimum. discount=10_percent_off means "0%–10% off," the opposite of what the name suggests and the opposite of Keepa's deltaPercentRange filter. Confirmed via docs (Rainforest's own wording: "Deals upto X% off") after a real side-by-side comparison against Keepa showed every single Rainforest result capped at exactly ~10% off, category after category — that uniformity is what triggered the check. First implementation had this backwards and would have shipped a category sync that silently excluded every deal deeper than 10% off. Fixed in rainforest.ts: uses discount=70_percent_off (the widest tier) plus minimum_rating=3_and_up as a quality floor, then sorts client-side by discount percent — the endpoint has no sort_by parameter at all (confirmed via docs), so a raw page comes back in Amazon's own order, not discount-descending.

2026-08-11
eb2bd8f

lightning-sync's completion log had gone silent for 3 weeks

The underlying work kept succeeding (confirmed via CloudWatch and Keepa API logs), but the process died before its final log line — found "terminating connection due to administrator command" in the error log. The shared pg.Pool had no 'error' listener: an idle connection dying in the background is normal for managed Postgres, but with nothing listening, Node's default is to crash the whole process, skipping every try/catch in the app. Added the listener — protects every cron and request sharing this pool, not just lightning.

—

Not caused by the category change — and bestsellers had the exact same bug

Checked whether the silent-cron issue correlated with adding Patio, Lawn & Garden (Aug 4) — it doesn't. ltsd-lightning's last completion log (even a skip warning) was Jul 20, two weeks before the category change. Separately, ltsd-bestsellers was found to have zero completion logs in its entire history — not "recently stopped," never once logged since it was built. Same signature as lightning: real work happening, process dying before the final log line. The Aug 11 pg.Pool fix applies to both, since it's the exact same shared pool.

Also found and fixed a related visibility bug while investigating: admin/logs' cron-status panel built its "last run per cron" data from one combined take:50 query across all 5 sources. High-frequency sources (category-feed logs many times a day) silently crowded low-frequency ones out of that shared window entirely — which is exactly how bestsellers and lightning's problems went unnoticed for weeks despite an admin panel that was supposedly monitoring this. Changed to 5 independent per-source queries, so every known cron always shows its true last-run state, however old or absent.

2026-08-11
825caa4

Found the actual root cause: not a crash, a 504 Gateway Timeout

The pg.Pool fix above was real, but incomplete — CloudWatch logs for ltsd-cron showed the true signature: lightning-sync and deal-sync?batch=0 calls returning a plain 504 after ~30-32s, with the Lambda's own orchestration logging "Batch 0 failed (504), stopping" and abandoning the rest of the batches. Measured every stage directly against production rather than guessing: Keepa's /deal + /product calls for a full 3-category, 81-item batch took 10.8s total — not the problem. The database-write phase took 332.2s — 97% of total time, averaging 4.1s per item with zero exceptions across all 81 items. Root cause: upsertDeal() did 5 sequential, one-at-a-time DB round trips per item (~400 for the whole batch), and redundantly re-upserted the same category row on every single item in a category.

Fixed with a shared per-run category cache (resolveCategoryId) and bounded concurrency (processConcurrently) applied to every sync loop, plus running seedDeals()'s categories 3-at-a-time instead of sequentially — concurrency split 3/3 across category and item levels, not higher, to stay near the pool's max of 10 connections rather than oversubscribing it. Re-measured the identical batch with the real production pool size: 342.9s → 24.1s, under the 30s gateway budget. Running categories concurrently introduced a real duplicate-write risk (same ASIN appearing in two categories syncing at once, racing on the price-history "already exists?" check) — closed with a synchronously-claimed Set shared across the run, race-free because JS's single-threaded event loop guarantees no other call can observe it between the check and the claim.

Swept the database for other issues while in there: found and deactivated 4 pre-existing deals with stale multi-year-old expiresAt values (unrelated legacy data, now cleaned up); confirmed "suspicious" 300-900-row price-history counts were genuine multi-month Keepa history, not duplicates.

2026-08-16
—

Rainforest's discount filter was backwards from what its name implies

First implementation of getDealsByCategory() used discount=10_percent_off expecting a Keepa-style minimum floor ("at least 10% off"). A real side-by-side comparison against Keepa (see §06) showed every single Rainforest result landing at almost exactly 10% off, category after category — suspiciously uniform. Docs confirmed the parameter is actually a maximum cap ("Deals upto X% off, 0%–X%"); the narrow tier was silently hiding every deal deeper than 10% off, the exact opposite of the intended quality filter. Fixed to use the widest tier (70_percent_off) plus minimum_rating=3_and_up, with results sorted by discount client-side since the endpoint has no sort_by at all. Re-ran the same comparison after the fix — results went from a flat 10% across the board to real 30–51% off branded products.

2026-08-16

Admin logs' "Keepa API Tokens" card had no source filter — silently broken the moment a second provider started logging

Both admin/logs/page.tsx and the orphaned admin/logs/keepa-status/route.ts queried the latest API_CALL log with no source filter, unlike cron-auth.ts's own getLastKnownTokens() which correctly filters to keepa:*. Invisible for months because Keepa was the only source that ever logged an API_CALL row — but real Rainforest test calls made during this migration's own verification work wrote rainforest:* rows into the same shared database, and the very next admin-logs page load would have shown "No data yet" for Keepa's token balance even though real, recent Keepa data existed. Fixed both queries to filter by source prefix; added a matching rainforest-status route and a second status card so the admin panel shows both providers' budgets side by side, with an Active/Inactive badge keyed off DEAL_API_PROVIDER.

2026-08-19
318c801…212db32

Rainforest migration merged to main and deployed — three real production bugs surfaced immediately after

The whole migration had only ever existed on a local feature branch, never pushed — Amplify's "last deployed 4 days ago" was accurate, and none of this work was live until merged into main and pushed for real. Once it was, real production traffic surfaced three separate, genuine bugs in quick succession, none of them Rainforest-specific:

1. Stale service-worker cache crashing /login after deploy. sw.js's CACHE_NAME never changed between builds, so the activate handler's own cleanup logic (which deletes any cache not matching the current name) never ran — returning visitors kept getting served JS chunks from builds the server had already deleted, producing a React hydration crash (#418) right after any deploy. Fixed by bumping the cache name and documenting that it needs bumping on every deploy that changes cached assets.

2. Service worker was caching authenticated pages, leaking sessions across accounts. Reported as: switching from a regular user account to an admin account in the same browser crashed reliably. Root cause: sw.js cached every HTML page — /login, /dashboard, /admin/* — "network-first" but with a cache fallback on any network blip. Since every one of those pages renders content specific to whoever's logged in, a stale cache entry from the previous session could get served during a different session, mismatched against its real data. Fixed by making pages network-only, falling back only to the static, generic offline page — never to a cached copy of a dynamic page.

3. Sign-out redirected to /login but didn't actually clear the session. A hard refresh landed straight back on the dashboard. Sessions here use JWT strategy — there's no server-side session to revoke, "signed out" means only the cookie clearing. Behind Amplify/CloudFront, Auth.js's protocol detection (and therefore which Secure/Host-prefixed cookie name it uses) can differ between the login request and the logout request enough that its own clear-cookie header doesn't match what was actually set, so the browser silently kept the old cookie alive. Fixed with an explicit backstop in logout(): delete every plausible Auth.js cookie name variant directly via next/headers' cookies(), rather than relying solely on Auth.js's own domain/prefix detection.

Separately (not a code bug): after adding RAINFOREST_API_KEY to Amplify Console, Rainforest calls kept failing with 401 "Supplied api_key is not valid" in production while the identical key worked fine called directly and on localhost. Confirmed the key itself was valid with a direct real call (200, real credits deducted) — the deployment that had already run didn't pick up the newly-added variable. Amplify's "redeploy" can re-serve an already-compiled build rather than rebuilding from scratch; forcing a genuinely fresh build (a new commit + push, not just clicking redeploy) is the reliable fix when a newly-added environment variable doesn't seem to take effect.
